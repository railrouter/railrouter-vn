# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RailRouter VN — a static PWA (no backend) that shows HCMC Metro (TP. Hồ Chí Minh) routes, stations and exits on a Mapbox GL map, with Vietnamese/English toggle. It's a fork of `cheeaun/railrouter-sg` (the Singapore equivalent), adapted for Vietnam.

**Important**: the `railrouter-sg/` directory at the repo root is the original Singapore project, kept on disk for reference only. It is not tracked by git, uses a different build tool (Parcel, not Vite), and is not part of this app. The real app lives at the repo root (`index.html`, `src/`, `vite.config.js`, `package.json`).

## Commands

```
npm install        # install deps
npm start           # vite dev server on :4567
npm run build       # vite build -> dist/
npm run preview     # preview the production build on :4567
npm run prettier    # prettier --write on src/**/*.json + root *.json (formatting only)
npm run format      # auto-fix [lat,lng]-order (Google) coordinate pairs back to GeoJSON [lon,lat], then npm run prettier
```

There is no lint or test setup in this repo. `npm run prettier` only covers JSON data files (`.prettierrc.json`/`.prettierignore` at the repo root) — it keeps GeoJSON/TopoJSON coordinate pairs like `[lon, lat]` on one line instead of `JSON.stringify(..., null, 2)`'s one-number-per-line output. JS/HTML/CSS are not Prettier-formatted; follow the existing inline-string-template style there instead.

**Pasting coordinates from Google Maps** (which shows `lat, lng`, the opposite of GeoJSON's `[lon, lat]`): paste them in as-is — don't hand-swap — then run `npm run format`. `scripts/fix-coords.cjs` (invoked by that script, before `npm run prettier`) walks every coordinate pair in `lines/*.geo.json`, `stations/*.json`, and `islands/vietnam-islands.geo.json`, and swaps any pair that looks like `[lat, lon]` back to `[lon, lat]`. This is safe specifically for Vietnam because latitude (~5–24) and longitude (~100–118) never overlap, so the correct order can be inferred from magnitude alone — no risk of misreading an already-correct pair. A pair outside both ranges is left untouched with a warning (probably a typo — check it by hand). Deliberately excludes `islands/hoang-sa.json`/`islands/truong-sa.json`: those are TopoJSON arc delta-encoded integers, not real lon/lat, and running this script on them would corrupt the data.

## Architecture

Single-page vanilla JS app (no framework), bundled by Vite. Entry point is `index.html` → `src/index.js`.

- **Map rendering**: Mapbox GL JS (`mapboxgl.accessToken` is hardcoded in `src/index.js`, reused from the SG project). Map is centered on HCMC but `maxBounds` is expanded to cover all of Vietnam so the Hoàng Sa/Trường Sa island layers are reachable.
- **Data files** (`src/`), split per region so each area's data can grow independently:
  - `lines/<region>.geo.json` / `stations/<region>.json` — one matching pair per region key. Current region keys: `tphcm`, `dongnai`, `hanoi`, `danang`, `cantho`, `haiphong`, `hue`, `khanhhoa`, `quangninh`, `bacninh`, `phuquoc-angiang`, `dalat-lamdong`.
  - **Region key naming convention**: a city that's centrally-governed or is otherwise its tỉnh's one obvious urban anchor keeps a bare `<city>` key — `hanoi`, `tphcm`, `danang`, `haiphong`, `cantho`, `hue`, `dongnai`, `quangninh`, `bacninh`. A city that's administratively just part of a larger merged tỉnh, but geographically cut off from the rest of that tỉnh's rail network by terrain/distance (so it could never simply become that tỉnh's shared bucket the way `dongnai` shares `tphcm`'s camera — see Region selector below), instead gets a `<city>-<tỉnh>` key: `phuquoc-angiang` (Phú Quốc, part of the post-2025-merger An Giang) and `dalat-lamdong` (Đà Lạt, part of Lâm Đồng). When adding a region, pick whichever of the two patterns fits.
  - `lines/*.geo.json` — GeoJSON `LineString` features for rail lines. Properties: `id`, `name`, `nameEn`, `color`, `status` (`operational`/`construction`/`planned`), `type` (`mrt`/`lrt`/`hsr` are rendered — see the `rail-lines-layer` filter; `rail` (conventional, non-high-speed) is not), `width`. A line is filed under whichever region it primarily runs through/toward (e.g. `thuthiem-longthanh` and `dongnai-line-1` are filed under `dongnai` since they head to Long Thành/Biên Hòa, even though they originate in HCMC). `thuthiem-longthanh` is split into `thuthiem-longthanh-segment-1`/`-2` (sharing `line: "thuthiem-longthanh"`) — unlike the `dongnai-line-1` split, this one *does* cross files: `-segment-1` (HCMC section) lives in `tphcm.geo.json`, `-segment-2` (Đồng Nai section) lives in `dongnai.geo.json`, matching where each segment's geometry actually falls. `dongnai-line-1` (formerly `line-1-segment-2b`, the HCMC Metro Line 1 extension into Đồng Nai) was deliberately given its own `line`/`id` prefix instead of staying grouped under `line-1` — it's treated as a Đồng Nai-owned line rather than an HCMC Line 1 sub-segment, even though geometrically it continues straight from Line 1's Suối Tiên extension.
  - `stations/*.json` — GeoJSON `Point` features per station, one FeatureCollection per region (an empty-features file is a valid placeholder, e.g. `hanoi.json`/most not-yet-populated regions until stations are added there). Properties include `id`, `name`/`nameEn`, `codes` (array of `{line, code}`), `lines`, `status`, and `exits` (array of `{number, name, description, location, status}`). Station building footprints and the exits layer are both derived from this data at runtime in `src/index.js` (not pre-baked).
  - `src/index.js` imports every region's `lines`/`stations` pair and lists them (except `dongnai`, see below) in `regionsConfig`, which drives two things: merging into single in-memory `railData`/`stationsData` FeatureCollections (the map always renders the full combined dataset regardless of region selection — see Region selector below), and the `#region-select` dropdown via `buildRegionOptions()`. `dongnai` is merged into `railData`/`stationsData` directly, outside `regionsConfig` — its rail always renders and its stations are tagged `region: 'tphcm'` (see Đồng Nai note below), but it never gets its own dropdown entry. When adding a new region: pick a region key per the convention above, create `lines/<region>.geo.json` + `stations/<region>.json` (even if stations starts empty), import both in `src/index.js`, add an entry to `regionsConfig`, add a camera preset to `regionBounds` (same key), and add an `i18nKey` translation pair in `src/i18n.js`. A region with zero line features is valid (e.g. `hanoi` today) and simply won't appear in the dropdown yet — see Region selector below.
  - `islands/hoang-sa.json` and `islands/truong-sa.json` — TopoJSON (GADM) polygons for the Paracel and Spratly islands, converted to GeoJSON at runtime via `topojson-client`. `islands/vietnam-islands.geo.json` — point features for smaller islands not covered by the GADM polygons. These render Vietnam's claimed territorial islands on the map; treat this as deliberate, not incidental, when editing map content.
  - Line/station colors and Vietnamese line names are duplicated as inline lookup objects inside `src/index.js` (`lineColors`, `lineNamesVi`/`lineNamesEn`) rather than read from the GeoJSON — keep these in sync if you add a line.
- **i18n** (`src/i18n.js`): plain object-based translation table (`vi`/`en`), no library. Current language is read from `localStorage['railrouter-lang']`. `t(key)` looks up the active language with a `vi` fallback. `updateTranslations()` in `src/index.js` re-applies `data-i18n`/`data-i18n-html` attributes in the DOM and calls `updateMapLabels()` to switch Mapbox `text-field` expressions between `name`/`nameEn` for stations, islands and archipelago labels. When adding UI text, add it to both language blocks in `translations` and reference it with `data-i18n`/`data-i18n-html` in `index.html` or via `t()` in JS.
- **Search**: Fuse.js fuzzy search over `stationsData.features`, keyed on `properties.name`/`nameEn`/`code` (key order flips depending on active language). Triggered from `#search-field`; results render via `showAllStations()`/the `oninput` handler, both producing the same `<li onclick="selectStation(...)">` markup. `selectStation` is attached to `window` since it's invoked from inline `onclick` HTML.
- **Station/exit detail panel**: `#station` sheet is populated by `showStationInfo()`/`showExitInfo()`, which build HTML strings with inline styles directly in JS (not componentized — follow the existing string-template style rather than introducing a templating layer).
- **Service worker** (`src/sw.js`, Workbox-based) is currently disabled — registration is commented out at the bottom of `src/index.js`.
- **Deployment**: `.github/workflows/deploy.yml` builds with `npm run build` and deploys `dist/` to GitHub Pages via `actions/deploy-pages`. `vite.config.js` sets `base: '/railrouter-vn/'` only for production builds (`mode === 'production'`), so dev (`npm start`) serves from `/`.

## Working with map/route data

Most historical commits are small, incremental edits to line geometry or station data (e.g. "Update line 1", "Update line 2"). When editing a file under `lines/` or `stations/`, keep `name`/`nameEn` pairs and `codes`/`lines` consistent across the matching line/station files for the same `id`, since the app cross-references them by `id` rather than by array position. A multi-segment line (one `line` value shared across several features with distinct `id`s, e.g. `line-1`/`line-1-segment-1`/`line-1-segment-extend`, or a line split across region files like `thuthiem-longthanh`) is referenced by stations via the shared `line` value, not any one segment's `id` — a station's `codes[].line`/`lines[]` entries should point at that shared value (or a plain line's own `id` when it isn't segmented), and it must actually exist on at least one feature in `lines/*.geo.json`.

- `phuquoc-line-1` (LRT sân bay Phú Quốc – Trung tâm Hội nghị APEC, in `lines/phuquoc-angiang.geo.json`) was originally interpolated from public reporting (ĐT.975 corridor, station Km markers), not an official survey/GIS file — treat its geometry as approximate unless/until verified against an authoritative source. Station ids are `pq-s0`..`pq-s5` with official names (Tây Bắc, Hà Nội, Huế, Tây Nguyên, Sài Gòn, Đảo Ngọc per Wikipedia's station table); `pq-s0`/`pq-s5` additionally connect to the airport/APEC Conference Center respectively, but those are connection points, not the station names themselves. `pq-s2`/`pq-s3` were repositioned along the existing line geometry (by projecting the official cumulative distance onto it, not by redrawing the line) to match their official km markers (7.970 km / 11.807 km of the 17.59 km line) — if the line geometry itself is later corrected, these two stations' positions should be recomputed the same way rather than left at their old fractional position.
- `dalat-thapcham` (the historic French-built Đà Lạt–Tháp Chàm rack railway, 1919–1932, dismantled after 1975; its restoration is floated — not committed — in the Đà Lạt 2050 urban master plan) is split by province per the usual cross-region convention: `-segment-1` (Tháp Chàm→Eo Gió, km 0–51, old Ninh Thuận/now Khánh Hòa) lives in `lines/khanhhoa.geo.json`/`stations/khanhhoa.json`; `-segment-2` (Đơn Dương→Trại Mát, km 56–77, Lâm Đồng) lives in `lines/dalat-lamdong.geo.json`/`stations/dalat-lamdong.json`, matching the two segments' shared boundary vertex at Eo Gió exactly (same pattern as `thuthiem-longthanh`'s cross-file split). Both segments are `status: "planned"` and `type: "rail"` (so they don't render on `rail-lines-layer`, same as the `rail` Bắc–Nam line) since the corridor no longer physically exists outside one short stretch. That stretch — Trại Mát→Đà Lạt, the real narrow-gauge tourist train still running today — is its own separate feature/`line` id, `dalat-tram-mat`, `status: "operational"`, sharing Trại Mát as a boundary vertex with `-segment-2`. Station ids are `dt-s0`..`dt-s10` (Tháp Chàm→Đà Lạt order); Trại Mát (`dt-s9`) carries codes/lines for both `dalat-thapcham` and `dalat-tram-mat` since it's the junction. All coordinates came from Google Maps links embedded in the English Wikipedia article's station table, except `dt-s1` (Tân Mỹ), which has no sourced coordinate and was linearly interpolated between Tháp Chàm and Sông Pha by its km marker — flag this if a real coordinate turns up. The line geometry itself is just straight segments between consecutive known station points (no polyline source exists for the original mountain/rack alignment), so treat it as a rough schematic, not real track shape. `lineColors`/`lineNamesVi`/`lineNamesEn` in `src/index.js` were updated with both ids — remember this step for any new line id, since a station referencing a line missing from those lookups renders a broken (`undefined`-colored/named) badge in `showStationInfo()`.

## Region selector

`#region-select` (top-left, next to the logo) lets the user reframe the camera to a preset defined in `regionBounds` in `src/index.js`, keyed by the same region key as `regionsConfig` (see Data files above — currently `tphcm`, `hanoi`, `phuquoc-angiang`, `danang`, `cantho`, `haiphong`, `hue`, `khanhhoa`, `quangninh`, `bacninh`, `dalat-lamdong`). Selecting one calls `map.fitBounds()` — it's camera-only, not a data filter; all lines/stations stay loaded regardless of which preset is selected. The bounds are rough framing boxes, not administrative-boundary-accurate polygons.

- **Dropdown population**: `buildRegionOptions()` renders `regionsConfig` in its fixed array order, but skips any region whose `lines/<region>.geo.json` has zero features — so a freshly-scaffolded empty region has a camera preset and is fully wired, but won't show up as a `<option>` until it gets at least one line feature. `bacninh`, `danang`, `hanoi`, `haiphong`, `hue` and `quangninh` are currently in that state.
- **Đồng Nai has no preset/dropdown entry of its own**: its urban area is contiguous with HCMC's, so its rail (`lines/dongnai.geo.json`) is concatenated straight into `railData` outside `regionsConfig`, and its stations are tagged `region: 'tphcm'` — picking `tphcm` reframes the camera to also cover it, and searching with `tphcm` selected includes its stations. It never gets its own `<city>`/`<city>-<tỉnh>` region key.
- **Search is scoped per region**: `currentRegion` tracks the active `#region-select` value (default `tphcm`); `getRegionStations()` filters `stationsData` by `properties.region`, and `rebuildFuse()` rebuilds the Fuse.js index over just that subset (plus the active language's key order) whenever the region or language changes. So switching regions changes both the camera and what search can find.
- **A region's bounds can deliberately overshoot its own tỉnh**: `dalat-lamdong`'s box extends southeast to include Ga Tháp Chàm (in Khánh Hòa, see `dalat-thapcham` above) rather than stopping at the Lâm Đồng border, since `fitBounds()` has no way to "focus" on part of a box — showing the whole historic line's southern end means zooming out past just Đà Lạt/Liên Khương. This is a one-off judgment call per region, not a new rule.
